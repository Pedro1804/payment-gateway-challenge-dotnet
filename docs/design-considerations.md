# Design considerations & assumptions

## Architecture

Three layers in a single project, split by folder:

| Layer | Responsibility |
|---|---|
| `Api/` | Controller, request/response DTOs, HTTP ↔ domain mappers |
| `Domain/` | Value objects, `PaymentProcessor` and `PaymentRetriever` services, `IAcquiringBank` and `IPaymentsRepository` ports, domain exceptions |
| `Infrastructure/` | `AcquiringBankClient` (HTTP to the simulator), `PaymentsRepository` (in memory) |

The domain only depends on its ports. Adapters are wired in `Program.cs`.

Each card field is a value object (`CardNumber`, `CardExpiry`, `Amount`, `Currency`, `Cvv`) that validates itself on construction, so a `CardPayment` is only ever built from validated values.

## API contract

### `POST /api/payments`

| Case | Response | Bank called | Payment stored |
|---|---|---|---|
| Authorized by the bank | `201` `status: "Authorized"` + `Location` header | yes | yes |
| Declined by the bank | `201` `status: "Declined"` + `Location` header | yes | yes |
| Invalid request | `400` `application/problem+json` with `paymentStatus: "Rejected"` and per-field `errors` | no | no |
| Bank failure (status ≠ 200, unreachable or timeout) | `502` problem "Acquiring bank unavailable" | yes | no |

- A payment declined by the bank is a created resource just like an authorized one, hence `201` in both cases.
- A rejection creates no payment: it has no id and cannot be retrieved with `GET`.
- The simulator's `503` (card ending in `0`) is translated into `502`: the failure comes from an upstream service, not from the gateway.

### `GET /api/payments/{id}`

- `200` with the same fields as the `POST` response.
- `404` if the id is unknown or is not a GUID.

### `GET /health`

- Liveness only: `200 Healthy` as long as the process serves requests.
- It does not check the bank, so a bank outage never makes an orchestrator restart the gateway; payments answer `502` instead.

### Format

- `id` is a GUID generated by the gateway. The bank's `authorization_code` is not kept.
- `status` is serialized as a string (`"Authorized"` / `"Declined"`).
- The card is only exposed through `cardNumberLastFour`, as a string to keep leading zeros.

## Validation

Two levels, both answered with `400 Rejected`:

1. **Deserialization** (ASP.NET): missing field, `null`, or wrong JSON type (`amount: 10.5`, `cvv: 123` as a number, `expiryMonth: "april"`).
2. **Domain** (value objects): business rules below. Only the **first** domain error is returned: construction stops at the first exception.

### Rule assumptions

| Field | Rule applied | Assumption |
|---|---|---|
| `cardNumber` | String of 14 to 19 ASCII digits | No spaces or dashes accepted |
| `expiryMonth` | Integer from 1 to 12 | |
| `expiryYear` + `expiryMonth` | Expiry month is not before the current month | The **current month is accepted**: a card is valid until the end of its expiry month. The reference date is the server's UTC date (`TimeProvider`) |
| `currency` | `EUR`, `USD` or `GBP` | Case-sensitive: `gbp` is rejected |
| `amount` | Strictly positive integer, in minor units | `0` and negative amounts are rejected. Bounded by `int` |
| `cvv` | String of 3 or 4 digits | Sent as a string to keep leading zeros |

## Storage

- `PaymentsRepository` is a `ConcurrentDictionary` registered as a singleton: payments are lost on restart, as allowed by the brief.
- Only the id, status, last four digits, expiry, currency and amount are stored. The full card number and the CVV are never persisted.
- Only `Authorized` and `Declined` payments are stored.

## Sensitive data

- `CardNumber`, `Cvv` and `BankPaymentRequest` override `ToString()` to mask the full card number and the CVV.
- Logs contain neither the card number nor the CVV: only the payment id, its status, the invalid field, and the bank's HTTP status or error type.

## Out of scope

- Merchant authentication and per-merchant isolation of payments: any caller can read any payment by its id.
- `POST` idempotency: two identical submissions create two payments.
- Retries towards the bank.
- A real database.

## Tests

- **Unit**: value objects, `PaymentProcessor`, `PaymentRetriever`, `PaymentRequestMapper`, `PaymentsRepository`, and `AcquiringBankClient` against a fake `HttpMessageHandler` (`FakeBankHandler`).
- **Integration**: full API through `WebApplicationFactory`, with the bank replaced by a substitute and a frozen clock (`FixedTimeProvider`), plus the `/health` endpoint.
- No automated test calls the Mountebank simulator. The end-to-end flow is described in [post-payment-examples.md](post-payment-examples.md).
